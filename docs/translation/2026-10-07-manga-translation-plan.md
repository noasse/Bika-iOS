# 日文生肉图片翻译（实验功能）

> **以 [工程设计与实践规划](2026-10-07-manga-translation-engineering-plan.md) 为准。** 本文保留早期验证记录；其中"Vision 对竖排完全不返回结果"一条已被修正：多列竖排时 Vision 可能跨列横读。

- 分支：`feature/manga-translation`
- 范围：只翻译图片里对话框中的日文；只做 iOS；只用端侧能力（Vision + Apple Translation）
- 不做：对话框外的文字（拟声词、压在画面上的旁白）、图像修复级抹字、macOS、云端引擎

---

## 一、开工前实测的事实

方案的每一步都建立在下面这些测量上，不是经验判断。

| 问题 | 结果 | 怎么测的 |
|---|---|---|
| Vision 能读横排日文吗 | ✅ 16/16 | 合成图，Hiragino 黑体/明朝 |
| Vision 能读竖排日文吗 | ❌ **0/7，且一个字都不返回** | 同上，1x 像素，带横排对照组 |
| 把竖排图旋转 90° 再读 | ❌ 0/7 | `VNImageRequestHandler` 的 orientation 参数 |
| Vision 能**定位**竖排文字吗 | ❌ `VNDetectTextRectanglesRequest` 返回 0 个区域 | 同上 |
| 竖排按字切块、横向重排后再读 | ✅ **7/7** | 同上 |
| 端侧 日→简中 | ✅ `LanguageAvailability` 返回 `supported`（需下载语言包） | macOS 27 |
| Vision 在 iOS 模拟器里能跑吗 | ✅ | 单元测试内调用 |

**两条由此得出的硬约束：**

1. Vision 既读不了竖排，也找不到竖排。**定位必须自己做**，识别前必须先**重排**。
2. iOS 18 上，`TranslationSession` 的直接初始化 `init(installedSource:target:)` 要 iOS 26；
   `translate(_:)` / `translations(from:)` / `prepareTranslation()` 是 iOS 18 就有的。
   所以在部署目标 iOS 18 下，翻译会话**只能**通过 SwiftUI 的 `.translationTask` 拿到——
   翻译服务要做成常驻在该闭包里、从队列取任务的工作循环。

> 测量过程里踩过的两个坑，记下来免得重踩：
> - 用 `NSImage.lockFocus` 画测试图在 Retina 上是 2 倍像素，按点坐标切图会全错位。用 1x 的 `CGContext`。
> - `kCTVerticalFormsAttributeName` 在横向 CTLine 里会把每个字**旋转 90°**，不是竖排排版。
>   要得到正立、带竖排字形（竖向的「ー」、右上角的「、」）的字，用 OpenType `vert` 特性。

## 二、流水线

```
页面 CGImage
  → 灰度位图（长边 ≤ 2000）
  → SpeechBubbleDetector   对话框 = 不接触页边的封闭白色区域；文字 = 它包住的深色"洞"
  → TextLineSegmenter      投影切列；合并字内空隙（川、小）；按宽度去掉振假名
                           横竖不靠几何硬判：两种读法都合理时都给出，由 OCR 置信度决定（竖排优先）
  → TextReflow             每列在"预期字界附近墨迹最少的那一行"下刀，避免把字切成两半；横向拼成一条
  → JapaneseTextRecognizer Vision 识别 + 修正重排造成的符号问题（竖「ー」读成 | 等）
  → [MangaTextBlock]       全部坐标为相对页面的 0–1 比例
```

坐标用比例而非像素或视图坐标，是因为阅读器会以不同尺寸解码同一页（横竖屏、缩放、解码分桶），
绑定到任何一种尺寸的覆盖层，在换成另一种尺寸时都会错位。

## 三、阶段

| 阶段 | 内容 | 状态 |
|---|---|---|
| **P1** 定位与识别 | 上述流水线 + 合成页面单元测试 + 仅 Debug 的调试覆盖层 | ✅ 完成 |
| **P1.5** 真机评估 | 用真实生肉检验识别效果——**整个实验的生死关** | ⏳ 等待真机结果 |
| P2 翻译服务 | 引擎协议；Apple 端侧实现（`.translationTask` 常驻循环）；测试用假引擎；按「图片 URL + 引擎版本」持久化缓存 | — |
| P3 接入阅读器 | 盖住原文贴中文；工具栏切换原文/译文；设置里「实验性」开关默认关；低优先级预取 | — |

**P1.5 之前不做 P2/P3。** 合成页面字体干净、背景纯白；真实页面有手写体、网点、压在画上的字，
效果一定更差。如果真实页面上对话框都找不准，后面的翻译和排版做得再好也没有意义。

## 四、如何在真机上评估（P1.5）

1. 用 Xcode 以 **Debug** 配置把 app 装到手机上（覆盖层只编进 Debug 包）。
2. 打开一本日文生肉，进入阅读器，点出工具栏。
3. 点右上角页码旁的 **取景框图标**，开启"文字识别调试"。
4. 每一页会显示：
   - 左上角：找到几个对话框、耗时多少毫秒
   - 蓝框：识别出的对话框
   - 红框 + 数字：每一列及其阅读顺序（应从右往左 1、2、3…）
   - 对话框下方黑底文字：`序号 縦/横 识别出的日文`

**值得记录的是：**
- 漏掉的对话框（没有蓝框）
- 误认的区域（蓝框套在了不是对话框的地方）
- 列顺序错误、列被切碎或合并
- 识别出的日文和原文的差别
- 每页耗时

挑 5–10 页有代表性的截图（普通对话、长台词、手写字体、有网点的页、对话框贴着画面的页）即可。

## 五、已知局限

- 只认**封闭的白色对话框**。边框断开、半透明、或文字直接压在画面上的都会漏。
- 列宽估计假设一列里至少有一个没有内部空隙的字（の、さ、本）；只由「川」「小」组成的一列会被切错。真实文本几乎不会出现。
- 重排后的符号修正只覆盖了「ー」和竖排省略号，其他竖排专用标点（「」『』〜）可能被误读。
