## 一、目标与边界

### 要做的

在 iOS 阅读器里，把漫画页面上的**日文**翻译成**简体中文或英文**，译文直接显示在原文位置，可随时切回原文。

### 硬约束

| 约束 | 含义 |
|---|---|
| 只用端侧能力 | 识别用 Vision，翻译用 Apple Translation。不上传图片、不需要账号与 API key、可离线 |
| 先只做 iOS | 部署目标 iOS 18。macOS 端翻译 API 需要 macOS 15，现目标为 14，暂不做 |
| 目标语言：简中 + 英文（必须） | 已实测日→简中、日→英、日→繁中三个方向在系统中均为 `supported`（需下载语言包） |
| 实验功能 | 设置里默认关闭，不影响现有阅读体验 |

### 明确不做（当前阶段）

- **拟声词**（ドキ、ズン 等）：字形高度变形，识别不可靠；汉化惯例也常不译。默认不处理，可后续单独评估。
- **图像修复级抹字**：用底色/局部取色覆盖，不做 inpainting。
- **云端引擎**：需求已明确只用端侧。
- **macOS**。

## 二、已确认的事实（决定架构的依据）

| 事实 | 来源 | 对架构的影响 |
|---|---|---|
| Vision 读横排日文可靠 | 合成页实测 16/16 | 横排文字（对话框内、画面上）直接交给 Vision |
| Vision **不能识别、也不能定位**竖排日文（单列/单块：0 个结果） | 合成页实测 0/7，`VNDetectTextRectangles` 0 个区域 | 竖排必须**自己定位**，再切块**重排成横排**后识别（实测 7/7） |
| 但多列竖排时，Vision 可能**跨列横读**出看似正常的假名汉字（`い本`、`い当`） | 第三轮测试中发现，修正了最初的结论 | 整页横排识别必须过滤这类误读（已实现：检测行上下是否紧贴墨迹） |
| 每次 Vision 调用固定开销约 250 ms | 分阶段计时 | 一页内所有对话框**拼成一张图一次识别**（4.5 s → 1.9 s） |
| iOS 18 上 `TranslationSession` **只能**经 SwiftUI `.translationTask` 获得；直接初始化需 iOS 26 | SDK 接口文件逐条核对 | 翻译服务必须是**挂在视图上的常驻工作循环**，不能随处创建会话 |
| `translate` / `translations(from:)` / `prepareTranslation` 在 iOS 18 可用 | 同上 | 可批量翻译、可预先触发语言包下载 |
| Translation 在模拟器能否工作 | **未验证** | M2 第一件事；若不能，翻译相关测试只用假引擎，真实效果只能真机验证 |

## 三、总体架构

```
            ┌─────────────────────────── 阅读器（ComicReaderView） ───────────────────────────┐
            │                                                                                │
 页面图片 ──▶ ① 识别层  MangaPageTextExtractor                                                │
 (已解码)    │   对话框检测 → 切列 → 重排 → 批量 OCR → 内容过滤                                  │
            │   画面横排文字（整页 Vision）→ 段落 → 跨列误读过滤                                  │
            │   画面竖排旁白（M4 新增）                                                         │
            │        │  [MangaTextBlock]  (日文 + 相对页面的比例坐标 + 类型)                       │
            │        ▼                                                                       │
            │ ② 翻译层  MangaTranslationService                                               │
            │   TranslationEngine 协议 ── AppleTranslationEngine（.translationTask 常驻循环）    │
            │                         └─ FakeTranslationEngine（测试）                          │
            │        │  [TranslatedBlock]  (原文块 + 译文 + 目标语言)                             │
            │        ▼                                                                       │
            │ ③ 缓存层  PageTranslationStore（磁盘 JSON，LRU 上限）                              │
            │        ▲   key = 页面图片 URL + 识别版本 + 翻译引擎版本 + 目标语言                    │
            │        │                                                                       │
            │ ④ 调度层  MangaTranslationQueue（由现有识别队列扩展）                                │
            │   一次一页、当前页优先、可取消；当前页之后预取 N 页（低优先级）                         │
            │        │                                                                       │
            │        ▼                                                                       │
            │ ⑤ 呈现层  MangaTranslationOverlayView（图片视图的子视图，随缩放）                    │
            │   对话框：底色覆盖 + 排版译文（竖/横自适应、字号适配）                                 │
            │   画面文字：局部取色底板 + 译文                                                     │
            │   工具栏「原文 / 译文」切换；设置：实验开关、目标语言                                   │
            └────────────────────────────────────────────────────────────────────────────────┘
```

### 各层职责与关键设计

**① 识别层（已有，继续迭代）**
- 输出唯一的数据结构 `MangaTextBlock`：日文、**相对页面的 0–1 比例坐标**、类型（对话框 / 画面文字）、方向。
- 比例坐标是贯穿全局的约定：阅读器会以不同尺寸解码同一页，绑定像素或视图坐标的结果一换尺寸就错位。
- 纯函数、无 UI 依赖、可在后台线程运行，全部用合成页面单元测试。

**② 翻译层（M2）**
- `TranslationEngine` 协议：`translate([String], from: ja, to: target) async throws -> [String]`。业务代码只依赖协议。
- `AppleTranslationEngine`：因为 iOS 18 只能经 `.translationTask` 拿会话，实现为挂在阅读器上的**宿主视图 + 异步队列**——视图出现时启动循环，从队列取批次调用 `session.translations(from:)`，视图消失时结束。
- **一页一批**：同页所有块一次翻译，既省开销，也让引擎看到更多上下文。
- 目标语言切换 = 更换 `TranslationSession.Configuration`，会话重建；队列中未完成的任务按新语言重排。
- 语言包未安装：用 `LanguageAvailability` 预检，`prepareTranslation()` 触发系统下载提示；未就绪时 UI 明确提示，不静默失败。

**③ 缓存层（M2）**
- 识别和翻译都很贵（识别约 1–2 s/页），看过的页不应重算。
- 两级：识别结果（与语言无关）+ 译文（按目标语言）。切换语言只需重翻，不重识别。
- key 中带**识别版本号与引擎版本号**：识别逻辑一改，版本号 +1，旧缓存自然失效，不会用旧的错误结果。
- 磁盘 JSON，按总大小 LRU 淘汰；设置页可查看占用并清除（与现有图片缓存设置一致）。

**④ 调度层（M3，由现有 `MangaTextRecognitionQueue` 扩展）**
- 已有：一次一页、最新请求优先、取消可达（真机卡死问题即由此修复，测试已验证）。
- 新增：**优先级**——当前页 > 预取页；预取当前页之后 2 页，滚走即取消。
- 识别与翻译串成一条任务：识别 → 存缓存 → 翻译 → 存缓存 → 通知呈现层。

**⑤ 呈现层（M3）**
- 覆盖层是**图片视图的子视图**（调试覆盖层已验证：静止与 2.4 倍缩放下位置都准确）。
- 对话框：用对话框**平均底色**覆盖原文区域，在 `textBounds` 内排版译文。中文竖排还是横排随框形自适应（细高框竖排，宽框横排）；英文一律横排。字号二分查找，填满但不溢出。
- 画面文字：不能涂白，否则盖掉画面。取文字周围的背景色做一块半透明底板，再放译文。
- 交互：工具栏一键切换原文/译文；长按某个块显示原文（便于核对）。

### 横切关注点

| 关注点 | 做法 |
|---|---|
| 隐私 | 全端侧；不新增任何网络请求 |
| 性能 | 识别批量化、队列限并发、缓存；目标：当前页翻译完成 ≤ 3 s（真机），预取页翻页即显示 |
| 可观测性 | 保留 Debug 调试覆盖层；新增「导出识别报告」（见第五节），用数据而不是截图评估 |
| 可回退 | 实验开关默认关；开关关闭时不运行任何识别与翻译代码 |
| 测试纪律 | 每个缺陷先写**能在旧代码上失败**的测试，修复后通过（本分支一直如此执行，并记录了"测试没有咬住"的情况） |

## 四、识别层剩余问题（第 4 轮）

| # | 问题 | 方案 | 难度 | 验收 |
|---|---|---|---|---|
| R1 | **画面上的竖排旁白**识别不到 | 整页找"大小一致、纵向对齐成列"的字形墨迹连通块 → 聚成列 → 复用切块重排、批量识别、内容过滤；排除已被对话框占用的区域 | 高 | 合成页：旁白被读出且画面线条不产生误报；真机：评估集中旁白召回率有可观提升 |
| R2 | **贴着图片边缘的对话框**被排除 | 允许触边，但要求形状紧凑（填充率高）、面积在合理范围、且不占据整条边（排除页面背景） | 中 | 合成页：贴边对话框被读出；页面背景仍不被当作对话框 |
| R3 | **黑底白字**对话框识别不到 | 深色均匀区域里找"明显更亮"的孔洞作为文字，反相后走同一流程 | 低 | 合成页：黑底白字被读出 |
| R4 | 整页横排识别每页 +0.8 s | 该遍改用较低分辨率；对比准确率与耗时后定参数 | 低 | 耗时下降且现有用例全部通过 |
| R5 | 第 3 轮修复未经真机验证 | 用评估集验证（见第五节） | — | 评估报告 |

## 五、评估方法：从截图改为数据

目前每轮都靠真机截图判断效果，问题有三：只能看个大概、无法比较前后两轮、截图里的画面内容也不便传递。改为：

1. **固定评估集**：你挑选约 20 页有代表性的页面（普通对话、长台词、手写字体、网点页、灰底/深色对话框、旁白、后记），之后每轮都用同一批页面。
2. **「导出识别报告」**（Debug 功能，M1 实现）：阅读器里一键导出当前章节每页的识别结果为 JSON——每个块的类型、方向、比例坐标、日文、置信度、耗时。**只含文字和数字，不含图片。**
3. 我基于报告做统计：每页块数、耗时分布、被过滤掉的内容、两轮之间的差异。漏检仍需你目测确认（例如"第 7 页右下的旁白没读到"），但描述即可，不必截图。

## 六、实践规划

按里程碑推进，每个里程碑独立可验收、可提交。工作量为相对估计：S = 半天以内，M = 约一天，L = 两天以上。

### M0 · 收尾与准备（S）
- 推送分支做备份（不开 PR）。
- 处理 `bika.xcscheme` 的 Xcode 自动改动（由你决定保留或丢弃）。
- `scripts/test.sh` 加 `-collect-test-diagnostics never`：测试失败时不再白等 10 分钟诊断收集。
- **验收**：远程有分支；本地工作区干净；CI 脚本更新。

### M1 · 评估工具（S–M）
- Debug「导出识别报告」（JSON，见第五节）。
- 你用当前代码跑一次评估集，作为基线。
- **验收**：拿到基线报告；对第 3 轮的修复给出真机结论。
- **依赖**：需要你在真机上操作。

### M2 · 识别第 4 轮（L）
- R2 贴边对话框 → R3 黑底白字 → R4 提速（先做低难度项，尽快见效）→ R1 竖排旁白（最难，放最后，单独提交）。
- 每项：合成页复现测试（确认在旧代码上失败）→ 修复 → 全套测试。
- 完成后用评估集再跑一次，与基线对比。
- **验收**：四项各有能咬住的测试；评估集对比报告显示改进、无明显退步。
- **决策点**：若 R1 误报过多，先以独立开关提供或推迟，不阻塞翻译。

### M3 · 翻译层与缓存（M–L）
- 第一件事：确认 Translation 在模拟器能否运行，决定测试策略。
- `TranslationEngine` 协议 + `FakeTranslationEngine` + `AppleTranslationEngine`（`.translationTask` 常驻循环）。
- 目标语言：简中、英文（繁中可零成本附带，是否开放由你决定）。
- 语言包检测与下载引导。
- `PageTranslationStore` 两级磁盘缓存 + 版本号失效 + LRU。
- **验收**：单元测试覆盖引擎协议、批处理、缓存命中与失效、语言切换；真机上日→中、日→英均能出译文。

### M4 · 呈现层与交互（L）
- `MangaTranslationOverlayView`：对话框底色覆盖与排版、画面文字底板、竖横自适应、字号适配。
- 工具栏原文/译文切换、长按看原文。
- 设置：实验开关（默认关）、目标语言。
- 调度：当前页优先 + 预取 2 页、滚走取消。
- **验收**：合成页快照测试（排版不溢出、缩放跟随）；真机连续阅读一章：不卡、译文位置正确、切换即时。

### M5 · 真机调优与收尾（M）
- 用评估集做一轮端到端评估：识别 + 翻译 + 排版。
- 性能、内存检查（长章节连续阅读）。
- 文档更新、整理提交、开 PR。
- **验收**：评估报告；PR 通过 CI。

### 依赖关系

```
M0 ─▶ M1 ─▶ M2 ─────────────┐
       └──────────▶ M3 ─▶ M4 ─▶ M5
```

M2（识别）与 M3（翻译）**可以并行**：翻译层只依赖 `MangaTextBlock` 这个已稳定的数据结构，不依赖识别细节。如果你更想早点看到中文，可以先做 M3、M4，再回头做 M2——代价是早期译文会受现有识别缺陷影响。

## 七、风险与应对

| 风险 | 可能性 | 影响 | 应对 |
|---|---|---|---|
| Translation 不能在模拟器运行 | 中 | 翻译层无法在 CI 中做真实测试 | 协议 + 假引擎覆盖逻辑；真实效果只做真机验收 |
| 端侧翻译对漫画口语、语气词质量一般 | 高 | 译文生硬 | 这是端侧方案的上限，本阶段接受；按块翻译并保留同页上下文 |
| 竖排旁白检测误报多 | 中 | 画面上出现乱码译文 | 内容过滤 + 跨列误读过滤；必要时独立开关或推迟 |
| 旧机型性能不足 | 中 | 翻译慢 | 缓存 + 预取 + 队列；评估时记录机型 |
| 语言包未下载 | 高（首次） | 无译文 | 预检 + 明确提示 + 一键触发下载 |
| 识别逻辑变化导致旧缓存错误 | 中 | 显示过时结果 | 缓存 key 带版本号，改动即失效 |

## 八、需要你决定的事

1. **顺序**：先做识别第 4 轮（M2）再做翻译（M3/M4），还是先做翻译尽快看到中文？我的建议是先 M0、M1 拿到基线，再先做 M2。
2. **繁体中文**：几乎零成本，是否一并开放？
3. **拟声词**：维持不翻译？
4. **评估集**：请准备约 20 页（第五节的类型）。
5. **默认目标语言**：简中还是跟随系统语言？
